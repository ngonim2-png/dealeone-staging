# Deploying DEALEONE to Render — step by step

This repo already has a `render.yaml` (a Render "Blueprint") that describes all three
pieces of the app — the Postgres database, the API, and the web frontend — so Render can
provision and wire them together in one go. You won't need to configure anything by hand
beyond the steps below.

What you'll need before starting:
- A GitHub (or GitLab) account, to hold the code — Render deploys from a git repo, not a
  zip upload.
- A Render account: [render.com](https://render.com) — free to sign up, no card required
  to deploy the free tier.
- The `dealeone-fullstack.zip` you already have.

---

## Step 1 — Push the code to GitHub

The zip isn't in a git repo yet, so this is a one-time setup.

1. Unzip `dealeone-fullstack.zip` somewhere on your computer and open a terminal in the
   resulting `dealeone/` folder.
2. Create a new **empty** repository on GitHub (no README, no `.gitignore` — just the bare
   repo) — call it `dealeone` or whatever you like.
3. In the terminal, run:
   ```bash
   git init
   git add .
   git commit -m "DEALEONE MVP"
   git branch -M main
   git remote add origin https://github.com/<your-username>/<your-repo>.git
   git push -u origin main
   ```
4. Double check `apps/api/.env` and `apps/web/.env.local` did **not** get committed — the
   repo's `.gitignore` should already exclude them, but it's worth a glance at
   `git status` before pushing. Those files hold local-only secrets/URLs; Render gets its
   own copies of what it needs from `render.yaml` instead.

## Step 2 — Create the Blueprint on Render

1. Log into the [Render dashboard](https://dashboard.render.com).
2. Click **New** → **Blueprint**.
3. Connect your GitHub account if you haven't already, then select the repo you just
   pushed.
4. Render will detect `render.yaml` at the repo root and show you a preview of what it's
   about to create:
   - `dealeone-db` — a managed Postgres database
   - `dealeone-api` — a Node web service (the Express API)
   - `dealeone-web` — a static site (the built React app)
5. Click **Apply** (Render may ask you to name the Blueprint — any name is fine, it doesn't
   affect the service names above).

Render will now build and deploy all three. This takes a few minutes — the API needs `npm
install` plus a Postgres connection, the web service needs a full Vite production build.
You can watch progress live in each service's **Logs** tab.

Two things happen automatically that you'd otherwise have to do by hand:
- `DATABASE_URL` is wired from `dealeone-db` straight into `dealeone-api` — no copying
  connection strings around.
- `JWT_SECRET` (the key that signs login sessions) is auto-generated by Render
  (`generateValue: true` in `render.yaml`) — there's no secret for you to create or paste
  in.

## Step 3 — Load the demo data (one time only)

The database migration (creating all the tables) runs automatically on every deploy as
part of the API's start command. Seeding demo listings/users does **not** run
automatically, since it wipes and reloads data — you don't want that firing on every
redeploy once real users exist.

1. Once `dealeone-api` shows **Live**, open it in the Render dashboard.
2. Go to its **Shell** tab (a terminal into the running service).
3. Run:
   ```bash
   npm run db:seed --workspace apps/api
   ```
4. You should see a line like `Seeded: 1 buyer + 10 sellers, 18 listings, 4 conversations,
   2 buyer requests.`

## Step 4 — Open it and check it works

1. Open `dealeone-web`'s service page in the Render dashboard and click its URL (something
   like `https://dealeone-web.onrender.com`).
2. You should land on the phone-number login screen with the logo.
3. Log in with the seeded demo number `+232-76-000001` (any name if it asks — that account
   already has one) to see the app pre-populated with listings, chats, and offers. Since
   there's no SMS provider connected yet, the one-time code is shown directly on screen
   instead of being texted (see the README's "What's still missing").
4. Try Explore, Search, and opening a listing to confirm the map and API calls are working
   end to end — if the API is unreachable you'll see an explicit "Can't reach the DEALEONE
   API" screen rather than something silently broken.

If that all works, you're deployed.

## If the default subdomains were already taken

`render.yaml` assumes the service names `dealeone-api` and `dealeone-web` are available,
which sets their URLs to `https://dealeone-api.onrender.com` and
`https://dealeone-web.onrender.com`. If someone else already has those (Render subdomains
are global), Render will have assigned different ones — check each service's page for its
actual URL, then:

1. On `dealeone-api`, open **Environment** and update `CORS_ORIGIN` to the web service's
   actual URL.
2. On `dealeone-web`, open **Environment** and update `VITE_API_URL` to the API service's
   actual URL.
3. Manually redeploy both (**Manual Deploy** → **Deploy latest commit**) so the change
   takes effect — the web service in particular needs a rebuild, since `VITE_API_URL` gets
   baked into the JS bundle at build time, not read at runtime.

## Free-tier things worth knowing before you rely on this

Render's free tier is genuinely free, but has a few limits that matter for a real deploy,
not just a demo:

- **The free Postgres database expires 30 days after creation**, then has a 14-day grace
  period to upgrade before Render deletes it. This is the one that bites people — mark a
  reminder, or upgrade `dealeone-db`'s plan in the Render dashboard before day 30 if you
  want to keep the data. (Upgrading is a plan change, not a rebuild — your data stays put.)
- **The free API service spins down after 15 minutes of no traffic** and takes about a
  minute to wake back up on the next request — so the first request after a quiet period
  will feel slow (a loading screen, then it responds). The static frontend
  (`dealeone-web`) doesn't have this problem; only `dealeone-api` (the Node service) does.
- Free web services share **750 instance-hours per month** across your whole Render
  workspace. One service running continuously is ~720 hours, so this is fine for a single
  API service but worth knowing if you add more free services later.
- None of this affects the deploy steps above — it's just what to expect once it's live,
  and what to budget for if you outgrow the free tier.

## Making changes later

Once this is deployed, any future code change is just: commit, push to `main`, and Render
auto-deploys both services from the new commit (this is on by default for Blueprint
deploys). No need to repeat the steps above — those are one-time setup. The one exception
is `db:seed`: only run that again if you deliberately want to wipe and reset demo data,
never against a database with real user activity on it.
